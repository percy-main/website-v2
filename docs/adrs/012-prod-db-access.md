# Decision 012: Production DB Access via Tailscale

**Date:** 2026-04-20
**Status:** Accepted (amended 2026-08-27 - on-demand router, see below)

## Decision

Give operators always-on access to the production PostgreSQL database via a
**Tailscale subnet router** running in the production VPC. Operators connect
to the tailnet from their laptops (Google OAuth sign-in, Tailscale free
Personal plan) and reach RDS at its private endpoint over WireGuard.

Two dedicated Postgres roles — `admin_ro` (default) and `admin_rw` (gated by
conscious connection choice) — are provisioned separately from the app's
master credentials.

## Architecture

```
  laptop (Tailscale app, signed in via Google Workspace account)
       ↓ WireGuard over the tailnet
  t4g.nano EC2 "subnet router" in public subnet
       ↓ VPC routing (advertised: 10.0.0.0/16)
  RDS PostgreSQL (private, SG allows 5432 from router SG)
```

- Public subnet placement forced by `enable_nat_gateway = false` — we deliberately
  don't pay ~$32/mo for NAT. SG has zero inbound rules, so the public IP is
  functionally unreachable.
- OAuth client secret (`tskey-client-...`) stored in AWS Secrets Manager,
  fetched by the EC2 instance via IAM role at boot.
- No SSH to the router. Break-glass via `aws ssm start-session` (SSM agent
  installed by user_data).
- IMDSv2 required, encrypted root EBS, source-dest check disabled (required
  for subnet routing).

## Database roles

| Role       | Privileges                                                                                                                                      | Intended use                    |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| `admin_ro` | `SELECT` on all tables + sequences (incl. default privileges for future)                                                                        | Day-to-day browsing, reporting  |
| `admin_rw` | `admin_ro` + `INSERT`/`UPDATE`/`DELETE`. No DDL, no `SUPERUSER`, no `CREATEROLE`, no `BYPASSRLS`. `statement_timeout=30s`, `log_statement=mod`. | Manual fixes. Use deliberately. |

Separate Postgres users (rather than one user with `SET ROLE`) so TablePlus
connection profiles can be labelled clearly — "Prod (RO)" and "Prod (RW)" —
making accidental writes harder.

Passwords auto-generated by `scripts/setup-db-admin-users.sh` and stored in
Secrets Manager at `percy-main-production/rds/admin-ro` and `admin-rw`.

## Options considered

1. **Tailscale subnet router (chosen)** — minimal ongoing cost (~$4/mo),
   lowest friction (open laptop, psql just works), uses an identity we
   already have (Google Workspace).
2. **AWS SSM Session Manager port-forward** — zero extra infra if we add
   SSM agent to an existing workload. More verbose invocation, requires AWS
   creds at connect time. Strong #2.
3. **Keep `bastion-sql.sh` only** — $0 steady-state but ~2 min wait per use;
   not viable for GUI exploration.
4. **AWS Client VPN** — rejected, ~$73/mo endpoint charge for solo use.
5. **Publicly-exposed RDS with IP allowlist** — rejected, exposes Postgres
   auth surface to the internet.

## Rejected alternatives within the chosen approach

- **SAML SSO via Google Workspace** — Tailscale Premium ($6/user/mo) only.
  Not worth it for one admin; sign-in-with-Google already uses the same
  Workspace identity and 2FA.
- **OAuth one-time auth keys** vs. reusable OAuth client secret — chose
  reusable so the router can self-reauth after reboots and AMI refreshes
  without operator intervention.
- **Tailscale SSH** to the router — rejected, we don't need shell access.
  SSM is a better break-glass.
- **CloudWatch alarm on anomalous `GetSecretValue` for the OAuth secret** —
  deferred. Would require standing up a CloudTrail → CloudWatch Logs pipeline
  just for one alarm. AWS account-level CloudTrail Event History (90 days)
  covers forensic lookback for this threat model.
- **Splitting the app user off RDS master** — tracked separately in issue #130.
  That's the bigger real risk; not bundled here because the role design,
  secret rotation, and verification belong in their own change.

## Bootstrap runbook

The ACL policy, subnet-router OAuth client, and its Secrets Manager value
are all managed by Terraform. The only manual step is **once** creating a
bootstrap OAuth client that Terraform itself uses to authenticate to the
Tailscale API.

### 1. Tailscale account

Sign up at https://tailscale.com using your Google Workspace account
(`alex.young@percymain.org` or similar). Free Personal plan is fine.

### 2. Bootstrap "trust credential" for Terraform

**Admin console → Settings → Trust credentials → New credential → OAuth**

- Description: `github-actions terraform apply — percy-main production`
- Scopes:
  - **Policy File** → Write
  - **OAuth Keys** → Write (called "OAuth Clients" in some UI versions)
- Tags: `tag:subnet-router` (Terraform needs to own the tag so it can
  delegate it to the subnet-router OAuth client it creates)

Copy the generated `client_id` and `tskey-client-...` secret and store as
JSON in Secrets Manager:

```sh
aws --profile percy-main --region eu-west-2 secretsmanager create-secret \
  --name percy-main-production/tailscale/terraform-oauth \
  --description "Tailscale OAuth client used by GHA to apply tf (Policy File + OAuth Keys scopes)" \
  --secret-string '{"client_id":"...","client_secret":"tskey-client-..."}'
```

(If the secret already exists, use `put-secret-value` instead to update.)

### 3. Terraform apply

```sh
cd infra/environments/production
terraform apply
```

This creates everything:

- Router EC2, SG, IAM role
- The `tag:subnet-router` tag owner, `group:db-admins` group, and RDS-only
  ACL in the tailnet policy
- A fresh OAuth client for the subnet router, with its secret written
  straight into `percy-main-production/tailscale/auth-key`
- `autoApprovers` on the 10.0.0.0/16 route so the router registers without
  manual approval

Verify: **Tailscale admin → Machines** should list `percy-main-production-router`
as online within a minute or so, with the 10.0.0.0/16 route approved.

### 4. Bootstrap DB roles

Make sure Tailscale is up on your laptop, then:

```sh
RUN_MODE=tailscale ./scripts/setup-db-admin-users.sh
```

This generates passwords, stores them in Secrets Manager, and creates the
two Postgres roles with the privilege grants described above.

### 5. Connection details for TablePlus / psql

Fetch the password:

```sh
aws --profile percy-main --region eu-west-2 secretsmanager get-secret-value \
  --secret-id percy-main-production/rds/admin-ro \
  --query SecretString --output text
```

Connection:

- Host: `percy-main-production-db.c3okmuekuxmm.eu-west-2.rds.amazonaws.com`
  (RDS endpoint — public DNS resolves to the private IP which is routable
  via the tailnet)
- Port: `5432`
- Database: `percy_main`
- User: `admin_ro` or `admin_rw`
- SSL: require

Label TablePlus connections distinctly — e.g. green for `admin_ro`, red for
`admin_rw` — so you know which you're in when pasting a query.

## Operational notes

- **Break-glass**: `scripts/bastion-sql.sh` is retained for the case where
  Tailscale is down or the router is broken. Test it quarterly by running a
  trivial query through it.
- **Patching**: EC2 is patched by SSM Patch Manager via the default baseline.
  Plan monthly `terraform apply` to pick up new AMI IDs (user_data triggers
  instance replacement via `user_data_replace_on_change = true`).
- **OAuth client rotation**: `terraform taint tailscale_oauth_client.subnet_router && terraform apply`
  replaces the client and rewrites the auth secret. The running router doesn't
  re-auth on the fly — either reboot the EC2 (`user_data_replace_on_change`
  triggers on AMI refresh anyway) or delete the router device in the
  Tailscale admin to force re-registration on its next restart.
- **Adding a second admin**: add their Google Workspace email to
  `var.tailscale_db_admins` in `infra/environments/production/variables.tf`
  and apply. They sign in to Tailscale with that account; nothing else to
  configure. DB passwords are in Secrets Manager (separate IAM).

## Amendment (2026-08-27): on-demand router (issue #720)

The router is no longer always-on. It is stopped by default and started per
access window with `pnpm run db:tunnel` (looks the instance up by its Name
tag, starts it, waits for running). A systemd oneshot enabled at
multi-user.target runs `shutdown -h +30` on every boot, so the instance
stops itself ~30 minutes after being started; the auto-assigned public IPv4
is released (and unbilled) while stopped. For a longer session, wait for the
stop and start again. Saves ~$12.50/mo (compute + public IPv4 + alarms).

Consequences:

- `enable_alarms` is now `false` in production - the StatusCheck alarms
  treat missing data as breaching and cannot coexist with a deliberately
  stopped instance. `scripts/bastion-sql.sh` remains the break-glass if the
  router is broken.
- The OAuth client secret is now used as
  `--authkey="$AUTH_KEY?ephemeral=false&preauthorized=true"`. OAuth-secret
  registrations are EPHEMERAL by default, and Tailscale garbage-collects
  ephemeral nodes while they are offline - which would have made the node
  vanish between access windows. Persistent registration keeps the node
  entry (shown offline) across stops.
